# Claude Code prompt: continue the Tessero parity program from the repository

You are the lead engineer of Tessero, a numerical computing platform for PHP. It has four parts:

- a C11/C++17 kernel, libtessero (`csrc/`);
- an FFI package (`src/`, namespace `Tessero\`);
- a Zend extension (`ext/`, namespace `Tessero\Ext\`);
- a Laravel bridge (`laravel/`).

NumPy 2.4.4 and SciPy 1.17.1 are the specification (ADR 0002). The mission is unchanged. Take Tessero to a
defensible, measured, near-complete implementation of the in-scope NumPy and SciPy surface, on both backends,
verified against NumPy and SciPy by generated fixtures. Coverage figures come from the code and the tests,
never from prose.

This prompt continues `prompts/numpy-scipy-parity-program.md` (the program). Read the program in full; its rules
still apply. This file adds three things: how to resume from the repository, what the first sessions learned,
and what to do next, in order. Work without stopping and without asking questions. Where a decision is
genuinely ambiguous, take the reading that keeps results verifiable, record it in `.work/decisions.md`, and
continue.

## 2. Rules added by the first sessions

These rules come from mistakes that were made and caught. They are binding in addition to the program's section 1.

**Reference and tolerances**
- Fixtures are generated only through `tools/parity/gen-fixtures.sh`, in the pinned numerical environment
  (ADR 0012); the generators refuse otherwise. On AVX-512 CPUs, NumPy's float64 transcendental loops differ
  from the C library by an ulp, and pinning removes that machine dependence.
- A fixture holds SciPy's plain output except under the generator rules in
  `docs/project/reference-deviations.md`:
  - guards where SciPy crashes;
  - undefined rows (AddressSanitizer or history dependence);
  - U1 and U2 upstream-bug rules;
  - tolerances derived per call from the call's own data, with a stated bound.

  A new deviation needs a new generator rule, its reason in that page, and a count generated by `report.py`.
  Never edit a fixture. Never add a hand-picked tolerance.
- A fixture for a function that is not implemented reports `missing`, not a failure. `missing` is never a way
  to hide a wrong result.

**Memory safety.** Every new kernel function must satisfy all of these:
- No C++ exception may reach C or PHP. Cores and routines are called through `cxx/fn_guard.cpp`; callbacks
  handed to vendored C code (QUADPACK, brentq) park exceptions and rethrow them after the C routine returns.
- Array sizes derived from parameters go through `tsd::alloc_count` (the memory budget, or RAM when no budget
  is set). No float-to-int conversion may be undefined: check the range, clamp axes, and reject NaN.
- Integer semantics follow NumPy: int64 with wrap-around (`CORE_INT64`), never float64 arithmetic that rounds
  above 2^53.
- Where SciPy crashes, return NaN, as narrowly as possible:
  - an argument guard only where SciPy is NaN just inside the guard;
  - otherwise a local fix on exactly the non-terminating path, recorded in `THIRD_PARTY_NOTICES.md`.

  Where SciPy raises, raise.

**Every phase ends with three checks, and each finding gets a regression case:**
1. The sanitizer sweep: `bash tools/parity/asan/run.sh`. It must report no SAN or CRASH lines. Hangs are
   acceptable only where SciPy itself runs the same algorithm; list those under "Known, not guarded".
2. An independent verification subagent that has not seen the implementation work. It picks at least 25
   covered symbols at random and writes fresh comparisons with new seeds and adversarial inputs, on both
   backends.
3. A new case in `tests/Unit/AdversarialInputTest.php`, or a fixture, for every finding.

**NumPy's conversions and exact integers** (learned in PAR-2.3)
- Where a value came from matters. A PHP int reaches the kernel exactly (`tsr_arg.ival`), a PHP list follows
  NumPy's Python-sequence rules (`flags` bit 1: `int()` of floats, range checks with `OverflowError`), and an
  NDArray follows ndarray rules (`'safe'` casting, `TypeError` for float indices). Probe NumPy with both a
  list and an ndarray for every new routine.
- Integer results must be exact above 2^53: 0-d ints carry `tsr_result.ival`; integer paths use int64 (or
  ranks in a sorted key table, as `unique` and the set operations do). The fixture runner compares integers
  exactly, so a float round trip fails there.
- Output dtypes that depend on a parameter are declared in the registry (`fn_keep`), never guessed by a binding.
- Kernel error codes choose the PHP exception class in both bindings (ADR 0013): use `TSR_EINDEX` for
  NumPy's IndexError and `TSR_ETYPE` for its TypeError.
- Where NumPy's own behaviour is undefined (a heap overflow, a segfault, an out-of-range cast), raise or return
  the defined value, add an adversarial case, and document it in `reference-deviations.md`.

**Build hygiene**
- If files are edited through a mount with lagging timestamps, delete `$BUILD/c` and `$BUILD/cxx` before a
  build that must include recent edits.
- After kernel changes, run `bash tools/sync-ext.sh`. The extension builds from `ext/libtessero`. A phpize build
  does not track header dependencies: after changing a header, rebuild the extension from a fresh copy.

## 3. First: cross-platform verification

The owner is about to run the full test suite on other operating systems. Make that possible and make its
results interpretable before feature work.

1. **Build on every CI target.** The targets are Linux x86-64 (glibc and musl), Linux arm64, macOS arm64 and
   x86-64, and Windows x64 (MSVC for the extension; the FFI DLL as `csrc/Makefile` and the release workflow
   build it). Run `.github/workflows/ci.yml` and fix what fails portably. Known work:
   - `ext/config.w32` compiles the C files with the C++ flag set. Give the C sources `/std:c11` and check
     `_Thread_local`, `NAN`/`INFINITY` and `__declspec(thread)` (see `csrc/src/fn.h` and
     `third_party/scipy/cdflib.h`).
   - `cxx/u128.hpp` has an MSVC fallback that has been tested on Linux (`-DTSR_PORTABLE_U128`: every stats
     fixture passes). Compile it with MSVC.
   - `long double` is 64-bit on MSVC and 128-bit on aarch64. The irwinhall fallback beyond 126 bits uses it,
     so check that fixture there.
2. **Separate "Tessero is wrong" from "the platform's libm differs".** The fixtures are pinned to glibc on
   x86-64. On another OS, NumPy calls that platform's libm, and so does Tessero. The specification there is
   NumPy on the same machine, so:
   - Generate the fixtures on that machine with `gen-fixtures.sh` into a scratch checkout. Do not commit
     them.
   - Run `run-tests.php` against them on both backends.
   - Record the outcome per platform in `docs/project/_generated/platforms.md`, generated by a small script
     from the `results.json` of each run.

   A function that passes against the local NumPy but fails the committed glibc fixtures is a libm
   difference. Document it; it is not a bug. A function that fails against the local NumPy is a bug.
3. Close TSR-108 (cross-CPU determinism) with that evidence, and update the "Verified on one platform" caveat
   in the gap analysis from the data.

## 4. Then: the remaining work, in this order

Each item runs the program's per-item loop (section 7): fixtures first, both backends, docs, ledger, metrics.
PAR-2.1 to PAR-2.3 are done; the ledger has the measured numbers. Two figures track progress, and both come
from `python3 tools/parity/report.py`:

- **Symbol coverage** (`docs/project/_generated/metrics.md`): every in-scope symbol counts once. This is the
  finish line of the program.
- **Usage-weighted coverage** (`docs/project/_generated/usage.md`): each symbol is weighted by how often the
  library code of 18 widely used Python packages calls it (`tools/parity/usage.py`, pinned tags). This is the
  figure developers see first. Its list "the most-called in-scope symbols not yet verified on both backends"
  orders the work inside every item below.

1. **Extension parity for the most-used functions** (part of Phase 4 of the ledger, TSR-101 to TSR-107). The
   most-called gaps are already verified on FFI and missing only on the extension:
   - `numpy.linalg` (`norm`, `inv`, `solve`, `pinv`, `matrix_rank`, `svd`, `det`, `lstsq`, `cholesky`),
     through the kernel so both backends share it;
   - `numpy.empty`, `round`, `allclose`, `isclose`, `ascontiguousarray`;
   - then `finfo`/`iinfo`, `einsum`, `asfortranarray`, `result_type`/`promote_types`.

   Re-run `report.py` after each group and record the usage-weighted change in the ledger.
2. **PAR-1.2, the non-ufunc `scipy.special` functions** (TSR-116): `comb`, `perm`, `factorial*`, `zeta`,
   `polygamma`, `spherical_*`, `logsumexp`, `softmax`/`log_softmax`, `softplus`, the `*_zeros` and `roots_*`
   families, `lqn`/`lqmn`, `stirling2`, `bernoulli`/`euler`, `ellip_harm*`, the `*vp` derivatives.
3. **PAR-1.3, complex operands in the registry** (TSR-116). This unlocks `hankel*`, `kelvin`, `wofz`,
   `sph_harm_y`, `lambertw` and the complex paths of the Bessel functions. Design it as an ADR:
   `complex128` inputs and outputs in the ufunc engine, with the same loop machinery.
4. **The rest of Phase 4: extension legacy gaps** (TSR-101 to TSR-107). These are the FFI-only modules (the
   full `Fft`, sparse, `optimize`, `.npz`, the missing `NDArray` methods). Bring them into the kernel or bind
   the existing kernel code, until M5 reaches 100 %. PAR-2.4 goes here too: the multivariate Generator methods,
   `permuted`, `bytes` and the extension's `choice` (TSR-309, TSR-105).
5. **PAR-3.4, the rest of `scipy.stats`** (TSR-304): multivariate distributions, resampling (`bootstrap`,
   `permutation_test`, `monte_carlo_test`, with SciPy's RNG consumption), `gaussian_kde`, `probplot`/`ppcc`,
   and the `make_distribution` API.
6. **Blocked items**: `poisson_binom` needs array-valued shape parameters (TSR-117); `barnard_exact` and
   `boschloo_exact` need `shgo` (TSR-118). Retry once each prerequisite exists.
7. **TSR-119 and TSR-120**: int64 comparisons in argpartition and nanargmin/nanargmax; a work budget for
   untrusted sizes.
8. **The program's phases 5 to 11**, in its order: dtypes and I/O; linalg, FFT and polynomials (`polyfit`,
   `roots`: TSR-306); integrate and interpolate; signal; optimize; sparse, spatial, cluster and ndimage; the
   closing pass. Within each, start with the most-called symbols of the usage report (`scipy.sparse` arrays,
   `scipy.optimize.minimize`/`brentq`, `scipy.linalg`).
