# Sorting: design, invariants and risk register

Tessero has three sorts with one result. This page records how they work, why their outputs are identical, where
the design could break, and which test covers each of those places. Speed figures and when to use which sort:
[benchmarks](benchmarks.md), section "Choosing a sort".

| PHP (both backends) | C | algorithm | memory |
|---|---|---|---|
| `NDArray::sort()` (default) | `tsr_sort` | LSD/MSD radix sort on 64-bit keys | scratch of 8 bytes per value (`tsr_alloc`, counted against the memory budget) |
| `NDArray::sortSimd()` | `tsr_sort_simd` | AVX2 quicksort in place, sorting-network leaves, multithreaded from 131,072 values | none (stack scratch only) |
| `NDArray::sortRuns()` | `tsr_sort_runs` | natural (run-adaptive) merge sort | 8 bytes per value plus the run table (`tsr_alloc`) |

Source: `csrc/src/sort.c` (all three, key maps, dispatch), `csrc/src/sort_qs.h` (the quicksort, a template included
once per key type), `csrc/src/sort_net.h` (the leaf networks, generated by `tools/gen-sort-net.php`).

## The contract

- Ascending order under one total order: numbers by value, **-0.0 before +0.0**, **NaN last**. Integers by value.
- NaNs are written back as the canonical quiet NaN (`NAN`): payload and sign are not kept. Arrays of fewer than two
  elements are returned untouched (a lone NaN keeps its payload). NumPy keeps NaN payloads; this is the one
  bit-level difference from `np.sort`, and it is shared by all three sorts.
- uint8 and bool use a counting sort (shared by all three entry points).
- The output is byte-identical across the three functions, CPU SIMD level, thread count, input alignment and the
  CPU's denormals-are-zero / flush-to-zero mode.

### Why the three outputs are identical

Each sort orders values by comparison of a key that is a **bijection of the bit pattern** (floats: the
order-preserving integer image `u ^ ((u >> 63) & 0x7fff...)`; integers: themselves). For a bijective key, equal keys
mean equal bits, so the sorted sequence of keys -- and therefore of bit patterns -- is unique, whichever comparison
sort produced it and in whatever order its steps ran. Two exceptions are handled explicitly: NaNs are removed before
sorting and written back canonically, and the float64 path of `sortSimd`, which compares doubles directly (where
-0.0 == +0.0), restores the zeros' signs afterwards.

## sortSimd architecture

1. **Dispatch** (`tsr_sort_simd`): AVX2 present (`__builtin_cpu_supports`, which includes the OS's YMM state
   check), GCC or clang on x86-64, dtype float64/float32/int64/int32 and n >= 2 -> the in-place path. Anything else
   (no AVX2, MSVC, non-x86, uint8/bool, complex) runs the radix sort, with the same result.
2. **Keys, in place, at the data's own width.**
   - int64 / int32: sorted as they are.
   - float32: mapped in place to int32 keys (the map is its own inverse), NaNs dropped in the same vector pass;
     mapped back after the sort, NaNs appended.
   - float64: sorted **as doubles** (AVX2 compares and min/max doubles in one instruction, int64 in three to
     five). NaNs dropped and negative zeros counted in one vector pass; after the sort the zero run (found by binary
     search) is rewritten: that many -0.0, then +0.0. If the calling thread has DAZ or FTZ set (MXCSR), the compares
     would treat subnormals as zero, so float64 then takes the integer-key route of float32.
3. **Quicksort** (`sort_qs.h`): pivot = median of nine fixed positions; partition four vectors (16 or 32 keys) per
   step from the end with less free space, lanes below the pivot moved by a permutation table and stored at both
   ends, 4 vectors held back at each end so a full store always fits; scalar branch-free tails. A pivot equal to
   the minimum splits off every key equal to it in one more pass (`x < QS_NEXT(p)`; `p + 1` for integers,
   `nextafter(p, +inf)` for doubles, skipped when p is the largest key). The smaller side recurses, the larger
   loops (stack depth <= log2 n); a depth limit of 2 log2 n + 4 levels switches to heapsort.
4. **Leaves** (up to 64 keys for 64-bit data, 128 for 32-bit): in-register bitonic sorting networks. Key slot i
   lives in register i % R, lane i / R, so short-distance steps compare whole registers; the flip form of the
   bitonic sort makes every compare-exchange ascending; one transpose writes the keys back. The networks are
   straight-line code generated by `tools/gen-sort-net.php` (do not edit `sort_net.h` by hand; regenerate with
   `php tools/gen-sort-net.php > csrc/src/sort_net.h`). Four or fewer keys (eight for 32-bit): insertion sort.
5. **Threads** (OpenMP; from `TSR_PAR_MIN` = 131,072 values, with the thread count of `tsr_set_threads`): the left
   part of each partition near the top becomes a task until parts are below n / (threads x 16) keys (at least
   16,384); each part is then sorted serially. Every thread of the team runs with the caller's MXCSR for the length
   of the sort and restores its own afterwards. Builds without OpenMP are serial.

## When the application itself is multithreaded

| situation | behaviour | guidance |
|---|---|---|
| several application threads sort **different** arrays at once | safe: the sorts keep no shared mutable state (tables are `const`, `sortSimd` allocates nothing; `tsr_alloc` is thread-safe) | none |
| several threads sort the **same** buffer at once (C API) | a data race, as with any in-place sort. PHP is not affected: `sort()`, `sortSimd()`, `sortRuns()` sort a fresh copy | do not share a buffer between concurrent in-place sorts |
| each of N application threads calls the multithreaded sort | each caller starts its own OpenMP team: N x threads workers (correct, oversubscribed) | set `Tessero::setThreads(1)` (extension: `tessero.threads=1`) when the application parallelizes itself |
| called inside the application's own OpenMP parallel region | nested parallelism is off by default, so the sort runs serially (correct) | none |
| worker threads left in a different MXCSR mode (DAZ/FTZ) than the caller | each team thread takes the caller's MXCSR for the sort | none |
| the process forks after a threaded sort | the child runs serially until the thread count is set again (`alloc.c`, `pthread_atfork`) | set threads again in the child if needed |

## Risk register

Each row: where the design could break, what guards it, and the test that would catch a regression. "Mutant"
refers to the mutation check below: the bug was planted on purpose and the suite failed.

| # | risk | guard | tests | mutant |
|---|---|---|---|---|
| R1 | the partition stores a full vector at both ends: a wrong hold-back or free-space computation overwrites unread keys or writes outside the subarray | 4 vectors held back per end; the side with less free space is read first (invariant: free space >= 1 vector before every store) | sizes 0..1100 exhaustive (`test_sort_hardening` 1), sizes 0..300 / 100,000 / 300,000 x patterns x misaligned starts (`test_sort_variants`), ASan, fuzz `sort` | M6 caught (8 checks fail) |
| R2 | a generator error in a network (lane layout, permutation, blend mask, transpose) | networks generated, never hand-edited; the committed header must equal the generator's output | 0-1 principle, exhaustive for n <= 16 (`test_sort_hardening` 2), every size 0..1100, fuzz | M3 caught (7 checks fail) |
| R3 | adversarial input drives the quicksort quadratic or the stack deep | median of nine; the smaller side recurses; depth limit -> heapsort | heapsort forced at depth 1, 4, 7 (`tsr_sort_test_depth`, test 4), equal pivot samples, organ pipe, sawtooth with period n/8 (test 3), fuzz bits 2-4 | M2 caught |
| R4 | the equal-minimum split: `QS_NEXT` must be the next key above p (integer overflow at the maximum, `nextafter` at -0.0, -tiny, the largest finite double, infinities) | p == largest key skips the split; `nextafter` for doubles | mostly-minimum / mostly-maximum data, float edge values (test 3), extremes (`test_sort_variants`) | M4a, M4b caught; M4 (an off-by-one in the all-elements-equal branch) is equivalent: no observable effect |
| R5 | float64 compared as doubles loses the zeros' signs (min/max may return the same zero twice) | negative zeros counted before the sort, zero run rewritten after | zeros only, zeros + subnormals + NaN (test 3), extremes, DAZ test | M1, M5 caught |
| R6 | NaN handling: payloads, negative NaNs, a NaN in every vector, all-NaN arrays, n not a multiple of the vector width | NaNs dropped (vector pass, scalar for a vector holding a NaN), written back canonically | extremes, float edge values, fuzz oracle (NaNs last and canonical) | M5 / M1 overlap |
| R7 | the caller runs with DAZ/FTZ: subnormals compare as zero | float64 checks MXCSR and uses integer keys | `test_sort_daz` (with and without DAZ/FTZ), fuzz bit 1 | -- |
| R8 | **worker threads** in DAZ/FTZ while the caller is not (MXCSR is per thread; found in this review) | every team thread takes the caller's MXCSR for the sort | test 5 sets DAZ in the workers only; without the guard it fails 3 of 3 | negative control caught |
| R9 | races between tasks, or a result that depends on the task schedule | tasks get disjoint parts; pivots do not depend on the thread count; the zero restore and NaN tail run after the region | 300,000-value cases at 1 and 4 threads (`test_sort_variants`, tests 3-4), PHP check 4 threads vs 1 thread on both backends | -- |
| R10 | concurrent use by the application (OpenMP threads, nested regions, pthreads each starting a team) | no shared mutable state | test 6 (application OpenMP threads, nested), `test_sort_app_threads` (4 pthreads x 4 sort threads) | -- |
| R11 | type punning: keys overlay float buffers | `may_alias` key typedefs; doubles are accessed as doubles | compiled at -O3 with GCC and clang (CI) | -- |
| R12 | uninitialized scratch (`TSR_NOINIT` skips the hardening zero fill) | every scratch element is written before it is read | ASan + UBSan suite (`make sanitize`), fuzz under ASan | -- |
| R13 | index arithmetic overflow | int64 indices; `lo + (hi - lo) / 2`; `p + 1` only below the maximum | extremes and integer limits (tests 3, `test_sort_variants`) | -- |
| R14 | CPU / compiler / build differences (no AVX2, clang, MSVC, no OpenMP, non-x86) | AVX2 checked at run time; every fallback is the radix sort (same result); `#ifdef _OPENMP` | CI: Linux gcc, clang sanitizer and libFuzzer jobs, macOS Intel (Apple clang, no OpenMP), Windows (MinGW), ARM (radix path) | -- |
| R15 | stack use | per-frame scratch <= about 1.3 KB; depth <= log2 n plus the heapsort cap | large-n tests, OpenMP worker stacks default | -- |
| R16 | speed regressions (not correctness): time depends on the input and on AVX2 | radix stays the default | benchmarks (`docs/project/benchmarks.md`) | -- |

## Tests

| test | where | covers |
|---|---|---|
| `test_sort_variants` | `csrc/tests/test_main.c` | 5 dtypes x random, duplicates, sorted, reversed, interleaved, NaN / signed zeros, extremes; n = 0..300, 100,000, 300,000; starts that are element- but not 32-byte aligned; 1 and 4 threads |
| `test_sort_daz` | same | float64/float32 subnormals and signed zeros with and without DAZ/FTZ in the caller |
| `test_sort_hardening` | same | an independent oracle (qsort over the documented order, so the radix sort is checked too) against all three sorts: (1) every size 0..1100; (2) 0-1 principle, exhaustive n <= 16; (3) 15 structured / adversarial / float-edge patterns at 1,000, 65,537 and 300,000 values; (4) heapsort forced; (5) DAZ in worker threads; (6) concurrent sorts from application OpenMP threads |
| `test_sort_app_threads` | same (not on Windows) | 4 application pthreads each running the 4-thread sort at once |
| fuzz `sort` | `csrc/fuzz/fuzz_sort.c` (CI 60 s per run, nightly) | random dtype / data, tiling past the parallel threshold with 4 threads (one input in eight), DAZ/FTZ, forced heapsort depth; oracle: the three outputs identical and ordered, NaNs last and canonical |
| PHP byte-identity | ad hoc, both backends | `sort == sortSimd == sortRuns` on every axis; 4 threads vs 1 thread on 400,000 values |

`tsr_sort_test_depth` (internal, `src/internal.h`) caps the quicksort's depth so the heapsort fallback can be
tested; it is hidden from the ABI and 0 outside tests.

### Mutation check (2026-11-05)

Planted bugs, one at a time, each against the full C suite:

| mutant | planted bug | result |
|---|---|---|
| M1 | zero-sign restore disabled | caught: 5 checks fail |
| M2 | heapsort skips its last swap | caught: forced-heapsort test (40 of 144 cases) |
| M3 | one compare-exchange flipped in the 32-bit 64-key network | caught: 7 checks fail |
| M4 | the all-equal branch of the minimum split off by one | not caught: equivalent mutant (every element equal, no effect) |
| M4a | integer `QS_NEXT` = p + 2 | caught: 5 checks fail |
| M4b | double `QS_NEXT` skips a value | caught: 3 checks fail |
| M5 | negative zeros not counted in the vector pass | caught: 5 checks fail |
| M6 | the partition tail drops one held-back key | caught: 8 checks fail; the fuzz target also aborts |
| R8 | MXCSR not propagated to worker threads | caught: test 5, 3 of 3 cases |

Rerun: `make -C csrc test`, `make -C csrc sanitize BUILD=./build-san`, `make -C csrc fuzz-standalone
FUZZ_TARGETS=sort FUZZ_REG_TARGETS= FUZZ_RUNS=1000000 BUILD=./build-fuzzsa` (or `make fuzz` with clang).

## Known limitations

- NaN payloads and signs are not preserved (canonical NaN), unlike NumPy; arrays of fewer than two elements are
  returned untouched.
- The extension's `sort()`, `sortSimd()` and `sortRuns()` sort the last axis; the FFI backend takes an axis.
- The fast path is AVX2 only: no AVX-512 or ARM NEON/SVE version yet (those machines run the radix sort).
- `sort()` and `sortRuns()` allocate scratch through `tsr_alloc` and can fail with a memory-budget error on very
  large arrays; `sortSimd()` does not allocate.
- Single-threaded, NumPy's sort (x86-simd-sort) is still slightly faster on float64, float32 and int32 random data
  (benchmarks); with 4 threads `sortSimd` is 2-2.6x faster.
